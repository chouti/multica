自部署运行时构建溯源

目标不是显示一个容易误导的版本字符串，而是让正在运行的 backend 与 frontend 可回答：它对应哪个官方 tag、精确来源是什么、这些判断有多可信，以及是否存在本地定制或部署错配。

Grounding Context

  • Release 已将 tag 与 commit 注入 Go backend，并将 NEXT_PUBLIC_APP_VERSION 注入 Web；但 server 尚未公开完整构建身份，Web 版本目前主要用于客户端 identity/analytics。
  • 已有公开 /api/config、可选 server_version 与 Help 显示路径；客户端必须以 optional/fallback 方式兼容旧 backend。
  • /health、/readyz、/healthz 分别承担 liveness/readiness 与 migration 检查，不应改变其成功语义。
  • 官方 Compose/Helm 用 tag 选镜像；本地 build 默认 backend 为 dev/unknown、frontend 固定 dev，正是溯源断点。
  • 外部模式支持：git describe 的 tag/commit/dirty 表达、OCI version/revision labels，以及 Next.js public env 的编译期冻结。

Topic Axes

Ranked Ideas

R1.统一 Build Provenance 契约，并自动为本地构建盖章

构建来源与官方基线信心 高复杂度 中

定义 backend、frontend、镜像与部署工具共享的结构化身份：official_tag、source_revision、official_baseline（exact/ahead/unknown）、build_kind（official/local）、source_tree（clean/dirty/unknown）与 built_at。本地 Compose build 在构建期从 Git 生成这些事实；没有可靠 Git 元数据时明确输出 unknown，而不是把 dev 静默隐藏。

Basis: direct: release 已传 backend VERSION/COMMIT 与 Web app version；本地 build 默认 dev/unknown。 external: git describe --dirty 可表述最近 tag、偏离与工作树状态。

Rationale: 直接回答“基于哪个官方 tag”，同时不把定制构建伪装成官方发布物；是其余诊断与部署能力的共同语义基础。

Downsides: 必须清晰规定字段来源与 unknown 语义，容器运行时不能自行猜测 dirty 状态。

R2.兼容优先地把结构化 Build Manifest 接入现有 /api/config

服务诊断/API 与可见性信心 高复杂度 低

先在已有公开配置响应中新增可选 build 对象，并保留简化 server_version；旧客户端忽略未知字段，新客户端以 schema fallback 读取。只有当缓存、权限或 payload 语义确实分叉时，才将该 manifest 拆成专用 diagnostics endpoint。

Basis: direct: /api/config 已被启动流程与 Help 使用，字段已采用 optional/loose 兼容模式；核验认为单独 endpoint 目前证据偏弱。

Rationale: 以最小的新网络面建立脚本、UI 和支持工具的权威事实源，并保持 API 兼容规则。

Downsides: 需要控制公共响应中暴露的 revision/时间精度，并防止 config 承担无界诊断职责。

R3.在 Help 提供 Web/API 溯源卡与有边界的支持包

服务诊断/API 与可见性信心 高复杂度 低

并列显示当前 Web bundle 的构建身份、API 的 Build Manifest、官方基线及可信度，并标出“匹配、混搭、未知”而不是简单字符串相等。提供一键复制的最小诊断文本/JSON，固定字段边界，不收集环境机密或无限日志。

Basis: direct: Web 已持有编译期版本、Help 已显示 server_version，Next public env 在 build 时冻结；这能观察浏览器实际拿到的静态产物。

Rationale: CDN 缓存、滚动升级或只更新一端时，用户截图就能携带足够事实，显著缩短支持往返。

Downsides: 客户端声明只能标为 observed，不能当作服务端可信事实。

R4.把 OCI labels 与嵌入构建事实做成双证据链

构建来源与官方基线信心 高复杂度 中

官方与本地镜像统一写入 OCI version、revision、created、source 等 label；运行时只回显同源、编译时嵌入的事实。必要时将 digest 作为部署注入的额外证据，使 docker inspect/registry 与 HTTP 诊断可以交叉核验。

Basis: direct: release 已产生 tag、sha tag 与部分 OCI labels，Go binary 已支持 ldflags。 external: OCI annotations 为 version/revision 提供标准语义。

Rationale: tag 可能重标；两条可独立查看的证据链可把“拉错镜像、盖章错误、运行漂移”区分开。

Downsides: 容器内不能可靠读取自身 label，必须在构建/部署期把要显示的事实显式带入。

R5.为 Compose 与 Helm 生成“期望部署”回执，并与运行产物对账

Compose/Helm/镜像部署链路信心 高复杂度 中

部署层记录所选 backend/frontend image reference、tag、可用的 digest、Chart appVersion 与 release revision；诊断界面将它们标为“期望部署事实”，再与组件自报的 artifact facts 并列。对 latest、组件分别 override、私有仓库或本地镜像，输出 match/mismatch/unknown，而非假设 Chart tag 就是真相。

Basis: direct: Compose/Helm 当前只表达期望 tag，Helm 可分别 override 两组件，release 同时产出 tag/sha/digest。核验确认 annotation 只能代表意图，不能冒充实际 imageID。

Rationale: 使升级排障能区分“values 写错”“rollout 未完成”和“运行 artifact 不符”。

Downsides: digest 取得能力因部署平台而异；不存在时必须诚实标注 absent。

R6.把可诊断性纳入 Release 的黑盒交付契约

Compose/Helm/镜像部署链路信心 高复杂度 中

Release CI 除构建和发布外，启动 backend/web 镜像并断言 API manifest、前端显示的构建身份、OCI labels 与 Chart appVersion 指向同一官方 tag。另设本地 build fixture，断言 unknown/定制状态不会伪装成官方 release。

Basis: direct: 流水线已分别构建 backend、web、镜像与 Helm chart，却没有证明这些值能被运行服务一致报告。

Rationale: 将最容易在后续发布脚本重构中漂移的“注入但不可见”链路变成可回归测试的产品契约。

Downsides: 增加 CI 时间与需要维护的端到端 fixture；应先锁定 R1 的稳定 schema。

Rejection Summary

候选结论
立即新建专用 build-info endpoint暂不独立推进：已有 /api/config 与 Help 通路，除非出现不同权限/缓存语义，否则重复建设。
在 health/readiness body 中直接塞版本拒绝：会模糊探针的稳定 liveness/readiness 语义；版本应为独立诊断事实。
所有响应都附 build header降级为未来补充：适合短指纹，但代理/缓存与前后端身份分离使它不适合主接口。
仅用 Helm annotation/Downward API 证明实际运行镜像拒绝：它只能投影部署意图，不能证明 kubelet 实际拉取的 digest/imageID。
运行时自动重建 Git dirty 状态拒绝：容器通常无工作树；dirty 必须是构建时事实或 unknown。
把 unknown/dev 静默隐藏拒绝：当前正是诊断断点；unknown 应是 R1 契约的一等状态。
