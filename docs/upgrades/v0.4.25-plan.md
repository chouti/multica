### Actuals vs plan (2 collisions the audit did NOT predict — both auto-merge semantic errors)

1. **`packages/core/api/schemas.ts` duplicate SkillSchema** (TS2300, caught by typecheck). The audit listed schemas.ts as a clean auto-merge (not in the 3-conflict set). Reality: fork (batch-import #2669) and upstream (refreshSkill) EACH independently ADDED `SkillSchema`/`SkillFileSchema`/`EMPTY_SKILL` to schemas.ts in DIFFERENT regions — 3-way merge kept both → duplicate identifiers. Merge-tree can't see this (regions don't overlap; no markers). **New collision type:** fork-add ∩ upstream-add of the SAME symbol in different file regions. Fix: removed upstream's duplicate block, kept fork's (positioned before BatchImportResponseSchema so the reference resolves; `.default()` ≡ `.optional().default()` runtime-wise). Deduped the `Skill` import.
2. **`task_source_task_id_test.go` arity** (caught by go vet). The audit's CompleteTask/FailTask landmine analysis EXCLUDED test files (`grep -v '_test.go'`), so it concluded "defused". Reality: the NON-test code is clean (Scenario B), BUT the fork has its OWN fork-added test (`task_source_task_id_test.go`, commit e25917f8e) that calls the old 7/8-arg signatures — upstream's signature change + test-caller updates couldn't reach a file upstream doesn't have. Fix: added `branchName=""` to 2 calls. **Lesson:** when upstream changes a function signature, the caller sweep MUST include `*_test.go` — fork-added tests are invisible to upstream's own update pass, and go build won't catch them (doesn't compile tests); only go vet does.

Both are exactly the "auto-merge ≠ semantically correct" class the skill warns about — caught by Phase 5 gates, not by merge-tree.
